# 2.3.57（本地 Windows 构建）

基于本机 2.3.56 的源码修改，保留额度恢复信号清理和长请求等待行为。没有上传 GitHub，没有停止正在运行的 Codex、管理器或网关。

## CPA fill-first 调度

- 默认 `accountRotationStrategy: "fill-first"`。普通模型请求按照使用池顺序选择第一个可用账号，持续使用到该账号不可用；使用池无可用账号时才进入备用池。较高优先级账号恢复可用后会重新参与选择。
- 保留 5 小时窗口剩余 **≤10%**、仅周额度窗口剩余 **≤3%** 的暂停线。不删除账号，不将保留线暂停记成服务端额度耗尽。
- 明确的 401/403、408、429、500/502/503/504、520–526 响应可以在未向客户端输出响应时换号，临时故障账号冷却至少 60 秒；更长的 `Retry-After` 会被保留。确认的额度耗尽沿用原有重置时间与恢复证据。
- 一次请求内依次尝试尚未尝试的可用账号，不反复扫同一账号。全部不可用时明确返回错误；不会为了复刻 CPA 的额外重试轮数而增加长时间等待。
- PAT 身份元数据查询或代理准备失败时可以换号；模型 POST 的传输状态不明确时只对后续请求冷却该账号，当前请求不跨账号重放。已经开始输出的流也不会自动重放。
- 不用普通 `session_id` 或缓存标识覆盖 fill-first 顺序。已确认的 `previous_response_id` 必须回原账号；未知绑定、账号处于保留线或冷却中时明确拒绝跨账号续聊。
- 保留手动切换。已激活的手动目标在同池内优先，仍受保留线、冷却和主池优先约束。额度测试请求不参与调度、不改变当前账号。
- 页面显示“CPA 优先”；当前账号信息仍以实际成功完成的请求为依据。轮换不触发 Codex 客户端重启。

这是在管理器原有本地网关中实现的 CPA 风格调度，保留管理器的主/备用池和安全重放限制，没有安装或运行另一个 CLIProxyAPI 服务。参考 [CPA 配置](https://github.com/router-for-me/CLIProxyAPI/blob/main/config.example.yaml)及 [FillFirstSelector](https://github.com/router-for-me/CLIProxyAPI/blob/main/sdk/cliproxy/auth/selector.go)。内部仍保留可选的 `round-robin` 和旧 `failover` 策略，默认使用用户选择的 fill-first。

## 验证与生效

隔离的本地 HTTP 上游验证了连续与并发请求、手动切换、严格续聊、10%/3% 保留线、身份/限流/服务故障、备用池接管、冷却恢复、真实额度耗尽识别、独立测试请求和关闭轮换。没有调用真实模型或使用真实账号凭据。另有启动回归、列表控件生命周期以及 100%/150%/200% 字体布局检查。

新包使用 v17 网关能力标记，旧 v16 的状态仍可读取。已经运行的旧程序不会因构建新包而热更新；下次启动新管理器时按已有安全升级机制接管网关，保留 Codex 客户端运行。
